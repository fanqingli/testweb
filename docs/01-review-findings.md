# 01 审阅结论与问题清单

> 审阅对象：《数据填报采集与任务协同系统》V1.2 脱敏详细版（第一至十二章）。
> 章节号均指原方案章节。严重度：**P0** 不解决则准确性、留痕或可落地性不成立；**P1** 影响协作效率或工程质量；**P2** 改进项。
> 每条问题的对应解法见 [02 优化方案](02-optimized-solution.md)、[03 Agent 调度设计](03-agent-orchestration-pi.md)、[04 实施路径与验收](04-roadmap-acceptance.md)。

## 1. 总体评价

原方案的骨架是对的，以下设计建议原样保留：

| 保留项 | 原章节 | 保留理由 |
|---|---|---|
| 计划 / 批次 / 单位任务 / 指标明细四级对象 | 2.1 | 批量监控与逐项退回可以同时成立 |
| AI 建议值、经办确认值、业务复核值、入库值分别保存 | 1.5 | 人机责任边界清晰 |
| 候选值必须绑定证据锚点 | 1.5、4.2 | 一值一档的基础 |
| 单位换算、合计校验等确定性计算不交给模型 | 1.5 | 可复现、可回归 |
| 分级签署、提交清单 manifest | 2.5 | 签署成本与风险匹配 |
| 批量操作固化对象快照、逐项返回结果 | 3.2 | 防止筛选条件漂移 |
| 版式能力包不得自动转正式 | 4.8 | 口径变化必须有人负责 |
| 识别失败不阻断人工填报 | 1.5 | 业务连续 |

主要不足集中在七个方面，按对目标的影响排序：

1. **采集通道单一**：全部材料都按“未知版式文件”去识别，没有利用“系统下发模板回收”“在线直填”“接口推送”这些零识别成本、准确率最高的通道。
2. **模型产数的边界没有封死**：只要求“数值锚定源单元格”，没有禁止模型直接输出数值，幻觉和抄错位的风险仍在。
3. **人工确认容易走过场**：逐项确认加高可信标识，实际会演变成“全部接受”；方案只度量 AI 准确率，不度量入库数据的最终差错率。
4. **留痕不防篡改、AI 过程不留痕**：`audit_log` 是可更新的普通表；模型版本、提示词版本、工具调用过程均未记录。
5. **没有 Agent 层**：第五章的 Skill 是固定工序，无法调度 Pi 这类通用 Agent 去处理长尾版式、编写能力包或辅助各角色办理。
6. **协作粒度粗**：单位内部只有“协作成员”一个角色描述，缺指标级分派、批注答疑、部分退回、数据复用、在途变更和更正流程。
7. **不可验收、不可排期**：质量与性能门槛全部写“按项目约定”，实施阶段顺序自相矛盾，技术栈只写“主流框架”。

## 2. 问题清单

### 2.1 P0

| 编号 | 原章节 | 问题 | 影响 | 建议方向 |
|---|---|---|---|---|
| F-01 | 1.3、2.3、4.1 | 只有“上传文件再识别”一条路。系统自己知道要采哪些指标，却不下发带绑定关系的模板。 | 把本可 100% 确定的导入变成概率性识别，人工确认量被放大。 | 分级采集通道 L0–L4，源头结构化优先（02 §3）。 |
| F-02 | 1.5、4.1、5.2 | 未规定大模型的输出形态。“数值抽取”“候选消歧”都可能由模型直接给出数字。 | 幻觉、串行串列、位数错误无法从机制上排除。 | 指针式抽值：模型只返回节点 ID，数值由程序从 IR 读取（02 §6.3）。 |
| F-03 | 5.3 | 可信度是加权分，阈值 0.85 / 0.60 没有标定依据；层级判定、风险分同样是未标定的加权公式。 | “高可信”并不对应可承诺的错误率，阈值无法验收。 | 用标注集按“档内错误率”反推阈值，并以双路一致、校验通过作为主要信号（02 §6.6）。 |
| F-04 | 2.3、6.6、10.1 | 逐项确认没有防自动化偏误的设计；质量指标只有字段准确率、人工修改率等 AI 侧指标。 | 经办与复核都可能“见高可信就过”，错误带签名入库。 | 三档确认、证据必看、关键指标盲录、事后抽检、入库差错率（02 §7）。 |
| F-05 | 2.1、2.4 | 指标明细主状态把流程（待确认、已入库）、AI 过程（AI 已预填、自检待完成、多候选待选）、值处置（无数据、不适用）、来源（人工补录）放进同一个枚举，与 2.4 “三类状态分别管理”的原则矛盾；3.4 又要求无数据项经复核认可，说明它不是终态。 | 状态组合表达不了（例如“人工补录且复核退回”），状态机实现必然打补丁。 | 拆成五个正交维度，任务状态由明细聚合派生（02 §5）。 |
| F-06 | 1.5、2.5、8.5 | `audit_log` 可更新可删除；`task_event` 与 `audit_log` 双轨且字段重叠；2.5 提到“审计日志完整性校验”但无机制；模型、提示词、工具调用未留痕。 | 留痕不能自证未被改动；AI 建议不可复现、不可追责。 | 只追加事件流加哈希链与定期锚定；三类记录统一信封；AI 运行档案（02 §8）。 |
| F-07 | 第五、七章 | Skill 是写死顺序的工序，没有 Agent 作业、工具授权、审批、轨迹的概念。 | 无法调度 Pi 等 Agent；长尾版式、能力包编写、异常诊断只能靠人。 | 新增 Agent 调度层：确定性流程编排，Agent 只做叶子节点（03）。 |
| F-08 | 11.1、11.2 | 第一阶段原型就验证 AI 预填，而 Document IR、Skill、自检放在第三阶段；看板原型在第一阶段、实现在第四阶段。没有把“零 AI 也成立的协同闭环”作为最小可用版本。 | 排期无法执行；AI 效果不达标会拖住整个项目。 | 先做协同闭环与确定性通道，AI 逐级叠加（04 §1）。 |
| F-09 | 1.2、10、11.3 | 识别质量、性能、验收门槛全部写“达到项目约定基线”。 | 无法验收，也无法判断方案是否可行。 | 给出分通道、分档位的建议指标与测量方法（04 §3）。 |

## 3. 原方案内部不一致清单
