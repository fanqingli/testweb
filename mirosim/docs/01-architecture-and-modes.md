# 01 总体架构与三种推演模式

## 1. 分层

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 场景包        policy            marketing            brand            │  刺激物类型、量表、行为选项、报告结构
├──────────────────────────────────────────────────────────────────────┤
│ 推演模式      panel 群体反应    deliberation 研讨    diffusion 传播    │  人物之间有没有、有怎样的相互作用
├──────────────────────────────────────────────────────────────────────┤
│ 实验层        实验设计 · 运行矩阵 · 对照 · 预算 · 效度闸门              │  版本 × 重复 × 模型族
├──────────────────────────────────────────────────────────────────────┤
│ 人物层        人物库 · 版本 · 长期记忆 · 态度 · 关系图 · 平行世界        │  跨实验长期存在
├──────────────────────────────────────────────────────────────────────┤
│ 分析层        聚合 · 配对比较 · 主题编码 · 稳定性 · 校准 · 报告          │  研讨模式另接 v3.0 的投票、共识、情绪等模块
├──────────────────────────────────────────────────────────────────────┤
│ 底座          模型网关（档位、录制、回放）· 确定性随机 · 存储 · 清单 · 台账│
└──────────────────────────────────────────────────────────────────────┘
```

场景包与推演模式是两个独立的维度，可以任意组合；常用的组合见 §6。

## 2. 核心对象

| 对象 | 是什么 | 数据契约 | 生命周期 |
|---|---|---|---|
| 人物 `persona` | 一个合成的人，有不可变的版本序列 | `schemas/persona.schema.json` | 长期 |
| 记忆 `memory_item` | 人物经历过的一件事，只追加 | `schemas/memory_item.schema.json` | 长期 |
| 世界 `world` | 一条时间线。基准世界是人物「真正的人生」；分支世界供实验使用 | `docs/06` | 基准长期；分支随实验 |
| 人群框架 `population_frame` | 这批人代表谁、各类占多少、各抽多少 | `schemas/population_frame.schema.json` | 可复用 |
| 刺激物 `stimulus` | 要评估的东西及其若干版本 | `schemas/stimulus.schema.json` | 可复用 |
| 实验 `experiment` | 一个问题 + 刺激物 + 人群 + 设计 + 量表 + 预算 | `schemas/experiment.schema.json` | 一次立项 |
| 运行 `run` | 运行矩阵中的一格：一个版本 × 一次重复 × 一个模型族 | `docs/06` | 实验内 |
| 反应 `response` | 一个人物在一次运行中的结构化反应 | `schemas/response.schema.json` | 永久保留 |
| 清单 `run_manifest` | 一次实验用了什么代码、输入、人物、模型、提示词、随机种子 | `schemas/run_manifest.schema.json` | 永久保留 |

术语沿用 v3.0 §3.3：`issue`、`scene`、`run`、`persona`、`round`、`turn`、`proposition` 的含义不变。
本设计新增 `experiment`（一组平行的 `run`）、`variant`（方案版本）、`replicate`（重复）、`world`（时间线）。v3.0 的一个 `scene` 对应研讨模式下某个版本的一次 `run`。

## 3. 运行矩阵

```text
            重复 1          重复 2          重复 3
版本 S0     run             run             run        ← 现状对照
版本 A      run             run             run
版本 B      run             run             run
版本 B'     run             run             run        ← 安慰剂：内容与 B 完全相同
                                                       × 模型族数（缺省 1）
```

- **同一批人物进入每一格。** 人物在各格之间互不知情，每格都从同一个基准世界快照出发。这使得每个人物都是自己的对照。
- **重复之间只有随机种子不同。** 重复用来量模型采样带来的波动。
- **模型族**用来量「换一个模型结论还成不成立」。正式结论至少两个模型族；探索性实验可以只用一个。
- 调用量上界 = 人数 × 版本数 × 重复数 × 模型族数（× 步数，仅传播模式）。超过 `budget.max_calls` 的实验在启动前被拒绝（`tools/validate_examples.py` 已实现此检查）。

## 4. 三种模式

| | 群体反应 `panel` | 研讨 `deliberation` | 传播 `diffusion` |
|---|---|---|---|
| 回答的问题 | 各类人各自看到后怎么反应，比例与理由是什么 | 利益不同的各方当面交锋，会卡在哪、能在什么条件下谈拢 | 消息在人与人之间传开之后，说法怎么变、态度怎么走 |
| 人物间作用 | 无 | 同场对话，多轮 | 沿关系图逐步传递 |
| 规模 | 100–1000 人 | 6–12 人 | 200–1000 人，3–6 步 |
| 每人调用 | 每版本 1 次 | 每版本 5 轮左右 | 每版本每步至多 1 次 |
| 输出 | 结构化问卷 + 一句原话 | 发言全文 + 私下立场 + 命题 | 每步的反应 + 转述链 |
| 人物模型档位 | economy | balanced；专家与法律角色用 reason | economy |
| 典型用途 | 文案、定价、条款措辞的多版本比较；找出该重点关注的人群 | 政策条款的博弈；渠道或加盟政策的谈判 | 危机回应；有争议的营销活动；政策被误传的风险 |
| 主要失真风险 | 讨好、参与度虚高、回答趋中 | 过快达成一致、人人讲理、话多者主导 | 人人转发、转述过于准确 |
| 实施阶段 | 第 1 期 | 第 3 期（接入 v3.0 设计） | 第 4 期 |

### 4.1 群体反应模式的流程

```text
1  载入实验配置 → 校验 → 估算调用量与成本 → 人工确认
2  按人群框架抽样：先复用库内人物（不低于 reuse_min_ratio），不足的由人物工厂补足并入库
3  锁定人物版本，取基准世界当前序号，写入清单
4  对每个 (版本, 重复, 模型族)：
     对每个人物（并发）：
       a  曝光判定（forced：一律看到；natural：按渠道抽签）        ← 代码
       b  检索相关记忆与既有态度                                    ← 代码
       c  渲染提示词，调用模型，录制原始输出                         ← 模型
       d  校验输出；不合格重试一次；仍不合格记为无效                  ← 代码
5  质检：有效率、参与度、方差、安慰剂差异、负对照（docs/03 §5、§6）
6  分析：聚合、配对比较、主题编码、稳定性（docs/05）
7  生成报告；写清单；可选：把选定版本提交进基准世界（docs/02 §5）
```

第 5 步不通过时停在这里，产出质检报告而不是结论报告。

### 4.2 研讨模式的流程

沿用 v3.0 第 4 章的阶段 0–7 与五轮结构。接入本设计时改四处：

1. **参会人物从群体反应的结果里挑**（§5），而不是只凭相关方地图指定。v3.0 的「② 象限里谁没被代表」这一问保留为必答项。
2. **每个方案版本各开一场**，同一批人物、从同一个世界快照出发。v3.0 的一个 `scene` 变成矩阵里的一格。
3. **谁发言、说多长由代码决定**；人物每轮先私下申报立场再公开发言（`prompts/deliberation_turn.md`）。
4. **分析模块读私下立场**。投票与共识用 `private_stance`，命题抽取用 `speech`，两者的差就是表面服从的度量。

v3.0 的投票、共识、情绪、舆情、人物画像、权重、台账、关系图、联动等模块设计不变，作为研讨模式的分析层。

### 4.3 传播模式的流程

```text
步 0  按渠道计划做首轮曝光 → 被曝光的人物各自反应（同群体反应模式）
步 k  对上一步 would_share=true 的人物：
        由代码按其关系与渠道抽出接收者（docs/03 §4）
        接收者看到的不是原文，而是转述者的 share.what 原话
        接收者反应；其既有态度取自本分支世界里上一步写下的记忆
步 N  结束。输出：每步的触达人数、态度分布、说法的变形链
```

每个版本、每次重复各用一个分支世界，步与步之间的记忆写在分支里，实验结束后分支封存，不并入基准世界。

## 5. 漏斗：从广到深

```text
群体反应（300 人 × 4 版本）
   │  找出：哪个版本差异最大、哪几类人最分化、每类人的主要理由
   ▼
挑人：每个关键分群取 1–2 人
   │  规则：一个取该分群的多数立场中理由最典型的（与主题众数一致）
   │        一个取少数立场中态度最强的
   │        性格上至少有一位高发言倾向、一位低发言倾向
   ▼
研讨（8–10 人 × 2 个最有争议的版本）
   │  看清：争议的结构、可交换的条件、谁会被谁说服
   ▼
（需要时）传播（针对预计会引发转述的版本）
```

挑人规则由代码执行并写入清单，避免人工挑选时无意中选了「会说话」的人物。

## 6. 场景包 × 模式的常用组合

| 问题 | 场景包 | 模式 |
|---|---|---|
| 条款有几种写法，各类相关方分别怎么看 | policy | panel |
| 条款谈不拢的点在哪，什么条件能换来支持 | policy | deliberation |
| 政策发布后会不会被传成另一个意思 | policy | diffusion |
| 几版文案或几个价位，哪个更能带来尝试 | marketing | panel |
| 渠道商、加盟商对新政策的博弈 | marketing | deliberation |
| 有争议的活动会不会翻车 | marketing | diffusion |
| 定位、口号、命名的比较 | brand | panel |
| 危机回应声明的选择 | brand | panel，再接 diffusion |

## 7. 技术选型

| 部分 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 与 v3.0 一致 |
| 数据模型 | Pydantic v2，从 `schemas/*.json` 生成或对照 | 运行时校验与 schema 文件同源 |
| 存储 | SQLite（WAL 模式）起步；并发写入成为瓶颈时迁 PostgreSQL | 单文件、零运维、支持事务与全文检索；表结构两者通用（`docs/06`） |
| 记忆检索 | 第 1 期：对象标签匹配 + SQLite FTS5；第 2 期起可加向量检索 | 记忆条目带结构化对象标签，标签匹配已能覆盖多数情形 |
| 模型调用 | 自写薄网关，走 OpenAI 兼容的 HTTP 接口；`asyncio` + 信号量控并发 | 需要完整控制录制、回放、重试与档位降级 |
| 命令行 | Typer | 第 1–3 期以命令行为唯一入口 |
| 分析 | pandas + scipy | 配对检验、自助法区间 |
| 报告 | Jinja2 生成 Markdown；需要时再转 HTML 或 PDF | 与 v3.0 产出物体系一致 |
| 接口服务 | FastAPI，第 4 期再做 | 先把内核跑通 |

v3.0 的技术栈是 Flask 加 JSON 文件。两处改动的原因：存储见 `docs/00` §3.2 末；Web 框架在第 4 期前用不到，届时若 v2.6 的 Flask 代码可用则沿用 Flask，不强求更换。
具体模型不在本文档指定，按 `config/model_tiers.yaml` 的档位配置，在第 0 期用探针测试选定。
